## 一、 專案背景與市場痛點

* **市場現狀**：台灣動漫活動類型多元，涵蓋動漫演唱會、海外聲優來台見面會、代理商主題展覽、同人誌販售會、主題快閃店與聯名咖啡廳等。
* **核心痛點**：資訊分散於各代理商官網、多個售票平台（KKTIX、拓元、ibon 等）、同人展官網與社群粉專，粉絲需要同時追蹤多處，容易錯過活動或開賣時間。
* **專案願景**：打造一個「**台灣主流動漫活動一站式聚合與提醒平台**」，讓在台灣的動漫迷只需看一個地方，就能掌握近期活動並收到開賣/舉辦提醒。

---

## 二、 專案策略與目標定位

* **涵蓋範圍（僅台灣）**：只收錄**在台灣舉辦**的活動（含線上但由台灣主辦/售票之活動）。日本 IP 的來台展覽、海外聲優/歌手來台演出仍屬收錄範圍；在日本舉辦的活動不收錄。
* **單一語系（繁體中文）**：
  * 目標受眾鎖定台灣本地動漫迷，介面與內容僅提供繁體中文。
  * 活動標題**保留來源原文**（多數台灣來源本即為中文；含日文作品名或聲優名時原樣呈現，不做翻譯）。
* **規模聚焦**：延續 v1 原則，只收錄一線代理商、主流售票平台與大型同人/綜合展，不手動收錄零散小型活動。
* **確定性自動化（No LLM）**：資料擷取、正規化、標籤與推播全部採用規則與字典，所有處理結果可重現、可除錯；規則無法處理的資料進入人工審核佇列，以「少量人工」取代「模型推論」。

## 三、 核心功能規劃（MVP）

1. **資訊聚合引擎 (Aggregator)**
   * 定時擷取台灣代理商、售票網與展覽官網之活動資訊。
   * 統一格式呈現：活動名稱、日期時間、地點（縣市 / 場館）、票價區間、開賣時間、官方購票/資訊連結。
   * **規則式標籤**：
     * **活動類型**：優先由來源推論（如 FF / CWT → 同人展；動漫節 / 漫博 → 綜合動漫展），其次以關鍵字字典比對（「快閃」「POP UP」→ 快閃店；「見面會」「Fan Meeting」→ 見面會）。
     * **地區**：由場館字典或地址中的縣市名稱對應至北 / 中 / 南 / 東 / 離島。
     * **作品 / 代理商 / 聲優**：維護一份含別名的關鍵字字典（例：「孤獨搖滾」「ぼっち・ざ・ろっく！」→ 同一標籤），比對標題命中即標註；未命中者不自動建立新標籤。
   * **跨來源去重**：以「正規化標題 ＋ 開始日期 ＋ 場館」規則判定同一活動（例：同一場快閃店同時出現在代理商公告與 KKTIX），合併為一筆並保留多個來源連結。
2. **活動瀏覽與篩選 (Discovery & Filter)**
   * 列表與月曆 / 時間軸檢視。
   * 篩選條件：**地區**（北 / 中 / 南 / 東 / 離島 / 線上）、**活動類型**（演唱會、見面會、展覽、快閃店 / 咖啡廳、同人展）、**代理商 / 作品標籤**、**日期區間**、**是否已開賣**。
3. **訂閱與推播通知 (Subscription & Notification)**
   * 收藏活動、訂閱代理商 / 作品 / 聲優標籤或活動類型。
   * 透過 Line 官方帳號或 Web Push 推送：新活動上架、收藏活動開賣前 / 舉辦前一天提醒（推播文案採固定中文模板，不需生成）。

> **現階段不包含**：站內售票、金流、選位；任何日本舉辦之活動；多語系介面與翻譯；LLM / AI 生成式功能；社群平台（X、Facebook、Instagram）貼文爬取。

## 四、 資料架構與合規規範

* **資料獲取模式**
  * 結構穩定之頁面（售票網活動列表、展覽官網）：以定時排程擷取，使用 CSS 選擇器 / 結構化資料（JSON-LD、內嵌 JSON）解析。
  * 提供 RSS / Atom 之來源：直接解析訂閱源。
  * **非結構化公告**（如代理商「最新消息」長文）：以規則抽取日期、地點、票價等欄位（日期/金額正規表示式 ＋ 場館字典）；任一必要欄位抽取失敗即標為「待審」，**不自動上架**，由營運者人工補齊後發布。
* **合規與商業倫理**（同 v1）
  * 遵守 `robots.txt`，每來源請求間隔 ≥ 數秒，更新頻率以每日為主，不對售票網進行高頻請求。
  * 僅保留詮釋性基本資料（名稱、時間、地點、票價區間），不轉載完整文案與宣傳主視覺。
  * 每筆活動強制附上官方購票 / 原始公告連結，導流回原平台。

## 六、 資料規模預測（推估值）

> 以下數字為依各來源**公開活動型態與頻率之經驗推估**，僅供容量規劃與排程設計參考，PoC 階段需以實際擷取結果校正。

### 6.1 年度活動數量推估

| 其它代理商（1–2 家） | 20–50 | 15–35 | |

| FF 開拓動漫祭 | 2–4 | 2–4 | 每年約 2 場主展 |

### 6.2 營運面推估

| 指標 | 推估值 | 說明 |
|---|---|---|
| 同時「未結束」的活動數 | **約 35–100 筆** | 活動平均自公告到結束約 1–3 個月 |
| 每月新增活動 | 約 12–30 筆 | 暑假與寒假檔期（7–8 月、1–2 月）為高峰 |
| 每日擷取請求數 | 約 40–160 次 | 8–9 個來源 × 列表頁數 ＋ 新活動詳情頁；每日 1 次排程（年度大展每週 1 次） |
| 需人工審核比例 | 約 15–30% | 主要來自代理商非結構化公告 |
| 人工審核工時 | 約 **每週 1–2 小時** | 以每週 5–12 筆待審、每筆 5–10 分鐘估算 |
| 結構化資料量 | 約 **1–3 MB / 年** | 每筆活動含標籤、來源連結約 2–5 KB |
| 原始頁面快照（選配，用於除錯 / 變更偵測） | 約 0.5–2 GB / 年 | 若僅保留最近 30 天可降至 < 200 MB |
| 標籤字典規模 | 約 100–300 個 | 代理商 ~10、場館 ~30、作品 / 聲優 ~100–250（人工維護） |

### 6.3 與 v1 規模比較（概估）

| 指標 | v1（台日 ＋ 三語） | v2（台灣 ＋ 繁中） |
|---|---|---|
| 資料來源數 | 15+ | 8–9 |
| 年度收錄活動數 | 約 1,500–4,000（日本端佔多數） | 約 165–360 |
| 每筆活動文字欄位 | ×3 語系 | ×1 |
| LLM 呼叫 | 每筆新活動 1 次以上 | **0** |
| 外部 API 金鑰 | LLM（± 翻譯服務） | 無（推播服務除外） |

**結論**：資料量級降至「數百筆 / 年」，單一 PostgreSQL（甚至 SQLite）即可輕鬆承載；擷取可由單一排程 Worker 完成，無需佇列或分散式架構。

## 七、 取消 LLM 後的風險與對策

| 風險 | 影響 | 對策 |
|---|---|---|
| 代理商公告格式自由，規則抽取失敗率較高 | 待審量上升、上架延遲 | 必要欄位缺漏即進待審佇列；MVP 先只接 1–2 家代理商，觀察待審比例 |
| 新作品 / 新聲優無法自動辨識為標籤 | 訂閱命中率下降 | 待審介面中提供「新增標籤 / 別名」快捷操作；每季依熱門新番更新字典 |
| 活動類型誤判 | 篩選結果不準 | 來源推論優先、關鍵字次之；誤判可人工覆寫並回饋至字典 |
| 來源網站改版導致選擇器失效 | 資料中斷 | 每來源設定「連續 N 次 0 筆」告警並推送至 Slack；擷取器以來源為單位獨立實作，易於修補 |
| 拓元、ibon 暫緩造成演唱會資訊缺口 | 部分未經代理商公告的演出漏收 | 觀察 PoC 期間漏收比例；必要時以人工補登或於後續版本重新評估 |

## 八、 專案推動藍圖

* **Phase 0：PoC 與規模校正（新增）**
  * 對 KKTIX、木棉花、CWT 三個代表性來源（分別代表高 / 低 / 中結構化程度）各實作簡易擷取器，實際收集 2–4 週資料，校正第六節之推估值與人工審核比例。
* **Phase 1：資料結構與擷取管線**
  * 定義活動 Schema（單語系）、場館 / 地區 / 標籤字典；完成全部來源擷取器、規則式正規化、去重與人工審核佇列。
* **Phase 2：前端瀏覽體驗**
  * 響應式網頁（RWD），繁中單語；列表 / 月曆檢視、多條件篩選、活動詳情頁與一鍵前往購票。
* **Phase 3：訂閱與推播**
  * 串接 Line 官方帳號或 Web Push，實現「新活動上架通知」與「開賣 / 活動前夕提醒」，完成 MVP 閉環。
